# 需求文档规则

## 功能划分

从用户可感知的能力划分功能点和功能模块。功能模块是相关功能点的聚合，帮助用户理解产品可以做什么；它不等同于代码目录、类、服务、库或设计架构模块。功能模块不承担高内聚、低耦合或开闭原则等设计职责，而是要保证从用户的视角来看是最容易理解和速览当前项目所有需求的。

即使任务提供了代码，也先从输入、用户操作、可见结果和异常反馈中提炼能力，再重组成功能点。不要把解析、缓存、序列化、数据类型、算法步骤等实现过程直接列为用户功能。

每个功能点包含以下内容，根据要求写成表格或是自然段形式：

| 项目     | 要求                                                                   |
| -------- | ---------------------------------------------------------------------- |
| 功能名称 | 使用用户可理解的动词和对象命名。                                       |
| 功能描述 | 用两至三句话说明用户目的、系统可见行为和必要限制。                     |
| 输入     | 写用户提供、选择或确认的内容，例如文件、路径、选项或操作。             |
| 输出     | 写用户获得、查看或用于后续工作的内容，例如结果、提示、报告或生成文件。 |

输入和输出不写具体数据类型、内部对象、表名或代码接口，而是从用户可以接触到的视角来表述。

## 推荐结构

1. 产品名称与概述：说明目标用户、产品用途和核心价值。
2. 范围与边界：说明解决的问题、前置条件和明确不覆盖的事项。
3. 用户业务流程：按用户操作顺序描述，并配 UML 活动图。图中只呈现用户动作、可见系统响应和业务判断，不暴露内部处理细节。
4. 功能模块与功能点：用树状 UML 功能模块分解图呈现模块与功能点的聚合关系，再按模块展开功能点及其输入、输出。
5. 非功能要求和验收要求：只保留与产品目标有关、能够确认的要求。

## 审阅要点

- 用户能从模块名称判断适用场景和可获得结果。不得出现所面向的目标用户角度无法理解的地方。
- 每个功能点都能独立说明输入、输出和验收表现。
- 功能模块图与功能点表一一覆盖，但无需映射设计模块图。
- 不暗示系统会执行范围外的计算、处理或外部操作。
